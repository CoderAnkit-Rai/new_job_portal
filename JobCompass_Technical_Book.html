Part I
Foundation & Project Setup

Chapter 1: Project Overview

1.1 What Is JobCompass?

JobCompass is a full-stack, microservices-based Job Portal Management System designed to connect job seekers with recruiters through a modern, responsive web application. The system enables job seekers to search for jobs, apply with a single click, upload resumes, and track application status in real time. Recruiters can post job listings, review applicants, manage hiring pipelines, and update application statuses — all through a polished, role-aware user interface.

The project is built under the com.capg (Capgemini) organization namespace and demonstrates enterprise-grade software engineering practices including:

  • Microservices decomposition — Six independent business services, each owning its own database
  • Event-driven architecture — Asynchronous communication via RabbitMQ for decoupled service interactions
  • API gateway pattern — Centralized routing, authentication, and role-based access control
  • Modern frontend — Angular 21 with standalone components, lazy loading, and TailwindCSS 4
  • Containerized deployment — Docker Compose orchestration of 13+ containers

1.2 System Actors

JobCompass recognizes three distinct user roles, each defined in the Role enum within the user-service:

RoleDescriptionPrimary Actions
JOB_SEEKERAn individual searching for employment opportunitiesBrowse jobs, search with filters, apply to jobs, upload resumes, track application status, manage profile
RECRUITERA hiring professional representing a companyPost job listings, review applicants, view resumes, update application statuses (shortlist, schedule interview, reject), close job postings
ADMINA system administrator with elevated privilegesAccess to admin-restricted endpoints (reserved for future use in the current implementation)

The role is assigned at registration time and embedded into the JWT token. Every subsequent request carries this role, which is validated at both the API gateway level and the individual service level, creating a defense-in-depth authorization model.

1.3 Core Features Summary

Job Seeker Features

  1. Smart Job Search — Multi-parameter search by keyword, location, company, salary range, job type, and experience level via the search-service
  2. One-Click Apply — Apply to any open job posting with a single API call; duplicate applications are automatically prevented
  3. Application Tracking — Real-time visibility into application status progression: Applied → Shortlisted → Interview Scheduled → Rejected
  4. Resume Management — Upload PDF/DOC/DOCX resumes via multipart file upload; maintain version history; view and delete resumes
  5. Profile Management — Update personal details including name, mobile number, skills, and professional headline
  6. Application Withdrawal — Withdraw applications that are still in the APPLIED status

Recruiter Features

  1. Job Posting — Create detailed listings with title, company, location, salary, description, employment type, and experience level
  2. Job Editing — Update existing job details via query parameter-based edit mode
  3. Job Closure — Close filled positions, triggering RabbitMQ events to update the search index and notify downstream services
  4. Applicant Review — View all applicants for a specific job with filtering and search capabilities
  5. Applicant Profile Inspection — Slide-over panel showing applicant details, skills, contact information, and downloadable resumes
  6. Status Management — Update application status with a dropdown selector directly from the applicant management table
  7. Dashboard Analytics — Overview cards showing open roles count, total applicants, shortlisted candidates, and scheduled interviews

The application is branded as JobCompass, using a compass (🧭) icon as its logo. The branding is implemented consistently across all components: the landing page navbar uses Lucide Angular's Compass icon, while the footer and legal pages use the emoji variant. The brand name renders as "JOB" in dark gray with "COMPASS" in blue (or red in the footer), with a small triangle (▲) superscript accent. This branding is defined inline within each component's template rather than through a shared brand component.

Chapter 2: Problem Statement & Objectives

2.1 Problem Statement

The modern recruitment landscape faces several critical challenges that traditional job portals fail to adequately address:

For Job Seekers:

  • Fragmented Experience — Job seekers must visit multiple platforms, fill out repetitive forms, and manually track applications across different systems with no unified view of their hiring pipeline.
  • Lack of Transparency — After applying, candidates often face a "black hole" effect where they receive no feedback about their application's progress, leaving them unable to plan their job search effectively.
  • Cumbersome Application Process — Many portals require lengthy multi-step forms for each application, discouraging candidates from applying to multiple positions.

For Recruiters:

  • Manual Pipeline Management — Without integrated tools, recruiters resort to spreadsheets and email chains to track applicants, leading to missed candidates and delayed responses.
  • No Centralized Applicant View — Viewing an applicant's profile, resume, and application status typically requires switching between multiple tools and systems.
  • Scalability Limitations — Monolithic job portal systems struggle to handle peak loads during hiring seasons and cannot be independently scaled based on which features are most heavily used.

From an Architectural Perspective:

  • Tight Coupling — Traditional monolithic job portals bind all features into a single deployable unit, making it impossible to update the search functionality without risking the authentication system.
  • Single Point of Failure — A bug in the notification module can bring down the entire application, including critical job posting and application features.
  • Technology Lock-in — Monolithic systems cannot leverage different technologies for different concerns (e.g., Redis for caching, Elasticsearch for search, RabbitMQ for events).

2.2 Objectives

JobCompass was designed with the following specific, measurable objectives:

  1. Build a role-based, responsive job portal supporting distinct workflows for Job Seekers and Recruiters with seamless role-based navigation and access control.
  2. Implement a microservices architecture with six independent business services, each owning its own PostgreSQL database, communicating via REST APIs and RabbitMQ message queues.
  3. Develop a modern Angular 21 frontend using standalone components, functional guards, HTTP interceptors, and lazy-loaded routes for optimal performance.
  4. Implement stateless JWT authentication with token generation at the user-service, validation at the API gateway, and header-based identity propagation to downstream services.
  5. Enable event-driven communication using RabbitMQ topic exchanges to decouple job creation, application submission, and resume upload events from notification and search indexing concerns.
  6. Provide real-time application status tracking with a four-state lifecycle (Applied → Shortlisted → Interview Scheduled → Rejected) visible to both seekers and recruiters.
  7. Support file upload and management with multipart file handling, path traversal prevention, content type detection, and version history for resumes.
  8. Containerize the entire system using Docker and Docker Compose for consistent development, testing, and deployment environments.
  9. Aggregate API documentation using SpringDoc OpenAPI with Swagger UI accessible through the API gateway, covering all service endpoints.
  10. Design for extensibility with clean separation of concerns, MapStruct mappers, global exception handlers, and externalized configuration via Spring Cloud Config Server.

Why Spring Cloud Gateway over Zuul or Nginx? Spring Cloud Gateway is built on Project Reactor and WebFlux, making it fully non-blocking and reactive. This is critical for an API gateway that must handle many concurrent connections efficiently. The gateway's JwtAuthFilter implements the GlobalFilter interface, which operates on reactive ServerWebExchange objects and returns Mono<Void>. This means JWT validation, role extraction, and header mutation all happen without blocking threads — a significant advantage over the deprecated Zuul 1.x gateway.

Why PostgreSQL over MySQL? PostgreSQL provides superior support for complex queries, JSON data types, and ACID compliance. Each microservice has its own dedicated PostgreSQL database (e.g., jobportal_user_db, jobportal_job_db, application_db), enforcing the database-per-service pattern that prevents tight coupling at the data layer.

Why RabbitMQ over Kafka? RabbitMQ was chosen for its simplicity and routing flexibility. The system uses a single Topic Exchange (jobportal.exchange) with routing keys like job.created, job.applied, job.closed, and resume.uploaded. This pattern allows multiple queues to bind to the same routing key (e.g., both notification-service and search-service listen for job.created events). For the current throughput requirements of a job portal, RabbitMQ's message-level routing and durable queues are more appropriate than Kafka's log-based architecture.

4.2 Service Communication Patterns

4.2.1 Synchronous Communication (REST)

The primary communication path is: Frontend → API Gateway → Target Service. The frontend never calls a microservice directly. All requests pass through the gateway on port 8080, which performs JWT validation and routes to the correct service based on URL path prefixes defined in GatewayRoutesConfig.java:

Path PrefixTarget ServiceInternal URL
/api/users/**user-servicehttp://user-service:8081
/api/jobs/**job-servicehttp://job-service:8082
/api/applications/**application-servicehttp://application-service:8083
/api/resumes/**resume-servicehttp://resume-service:8084
/search/**search-servicehttp://search-service:8086
/notifications/**notification-servicehttp://notification-service:8085

Additionally, the application-service uses OpenFeign to call the job-service directly for inter-service communication. This is defined in JobClient.java — a declarative Feign interface with a JobClientFallbackFactory for circuit breaker resilience.

4.2.2 Asynchronous Communication (RabbitMQ)

For operations that should not block the caller, JobCompass uses RabbitMQ event publishing. When a recruiter creates a job, the job-service saves the job to its database and then publishes a job.created event. This event is consumed by both the search-service (to index the job for searching) and the notification-service (to log or email notifications).

4.3 Authentication Architecture

Authentication follows a stateless JWT model with a clear separation of concerns:

  1. Token Generation (user-service): When a user logs in with valid credentials, the JwtUtil class in user-service generates a JWT containing the user's email as the subject and their role as a custom claim. The token is signed with HMAC-SHA256 using a shared secret key and has a 1-hour expiration.
  2. Token Transmission (frontend): The Angular authInterceptor automatically attaches the token as a Bearer token in the Authorization header of every outgoing HTTP request.
  3. Token Validation (API gateway): The JwtAuthFilter (a GlobalFilter) intercepts every request, extracts the token, validates the signature and expiration, and extracts the email and role claims.
  4. Identity Propagation (gateway → services): After validation, the gateway mutates the request to add X-User-Email and X-User-Role headers before forwarding to the target service. Downstream services trust these headers implicitly.
  5. Authorization Enforcement (services): Each service performs role-based checks in its service layer (e.g., "only JOB_SEEKER can apply") and ownership checks (e.g., "you can only withdraw your own application").
Key Design Decision: The JWT secret key (mysecretkeymysecretkeymysecretkey) is shared between the user-service (which generates tokens) and the api-gateway (which validates them). This is configured via Spring Cloud Config Server properties. Individual business services do NOT validate JWT tokens — they rely entirely on the gateway-injected headers.

4.4 CQRS-Lite Pattern

The search-service implements a simplified version of the Command Query Responsibility Segregation (CQRS) pattern. The job-service is the system of record — it owns the canonical job data. When a job is created or closed, an event is published to RabbitMQ. The search-service consumes these events and maintains its own read-optimized copy in a separate database (job_search_db). This allows the search service to have a different data model, different indexes, and different query capabilities than the job service.

For example, the search-service's Job entity does not have fields like createdBy or createdAt that exist in the job-service. Instead, it focuses on searchable fields like title, location, company, skills, and salary. The search repository provides derived query methods such as findByStatusAndTitleContainingIgnoreCaseAndLocationContainingIgnoreCase() that would be unnecessarily complex on the job-service's database.

Chapter 6: Angular Fundamentals Used in This Project

6.1 Standalone Components

Angular 21 enables components to declare their own dependencies without NgModules. Every component in JobCompass uses this pattern:

@Component({
  selector: 'app-dashboard',
  standalone: true,
  imports: [CommonModule, FormsModule, NavbarComponent, FooterComponent],
  template: `...`
})
export class DashboardComponent implements OnInit { ... }

The imports array replaces what would traditionally be in an NgModule's declarations and imports. Each component is fully self-contained — it declares exactly which Angular modules (CommonModule for *ngIf/*ngFor, FormsModule for [(ngModel)]) and which sibling components (NavbarComponent, FooterComponent) it needs.

6.2 Functional Guards

JobCompass uses Angular's modern functional guard pattern instead of class-based guards. The authGuard is a CanActivateFn — a simple function:

export const authGuard: CanActivateFn = () => {
  const authService = inject(AuthService);
  const router = inject(Router);
  if (authService.isLoggedIn()) return true;
  router.navigate(['/login']);
  return false;
};

The roleGuard is a guard factory — a function that returns a CanActivateFn, allowing parameterized role checks:

export const roleGuard = (allowedRoles: string[]): CanActivateFn => {
  return () => {
    const role = inject(AuthService).getRole();
    if (allowedRoles.includes(role)) return true;
    inject(AuthService).redirectByRole();
    return false;
  };
};

Routes use this as: canActivate: [authGuard, roleGuard(['JOB_SEEKER'])]

6.3 HTTP Interceptors (Functional)

The authInterceptor is registered as a functional HttpInterceptorFn in app.config.ts via provideHttpClient(withInterceptors([authInterceptor])). It intercepts every outgoing HTTP request and adds two headers:

  • Authorization: Bearer <token> — for JWT authentication
  • ngrok-skip-browser-warning: true — to bypass ngrok's browser interstitial page in production

6.4 Lazy Loading with loadComponent()

Every route in app.routes.ts uses dynamic import() syntax for code splitting:

{
  path: 'recruiter/dashboard',
  canActivate: [authGuard, roleGuard(['RECRUITER'])],
  loadComponent: () => import('./features/recruiter/components/dashboard/dashboard.component')
    .then(m => m.DashboardComponent)
}

This means the DashboardComponent's JavaScript bundle is only downloaded when a recruiter navigates to /recruiter/dashboard. Job seeker components are never loaded for recruiters, and vice versa. This significantly reduces the initial bundle size.

6.5 Dependency Injection (providedIn: 'root')

All services in JobCompass use tree-shakable providers with @Injectable({ providedIn: 'root' }). This means each service is a singleton automatically registered at the application root without needing to be declared in any module's providers array. The Angular compiler can also tree-shake unused services.

6.6 Reactive HTTP with RxJS

All API calls return Observable<any> and are consumed with .subscribe() in components. Notable RxJS usage includes:

  • forkJoin() in MyApplicationsComponent — fetches job details for multiple applications in parallel
  • switchMap() in ResumeService.updateMe() — chains two HTTP calls: first GET the user, then PUT the update
  • catchError() with fallback in MyApplicationsComponent — tries search-service first, falls back to job-service

6.7 Manual Change Detection

Nearly every component in JobCompass injects ChangeDetectorRef and calls this.cdr.detectChanges() after asynchronous operations. This is because data changes inside subscribe() callbacks may not automatically trigger Angular's change detection cycle, especially in components with OnPush strategy or deep callback nesting. While Angular's default change detection would usually handle this, the explicit calls ensure UI consistency across all scenarios.

6.8 Environment-Based Configuration

The application uses Angular's environment files to switch between development and production API endpoints:

// environment.ts (development)
export const environment = {
  production: false,
  apiUrl: 'http://localhost:8080'
};

// environment.prod.ts (production)
export const environment = {
  production: true,
  apiUrl: 'https://dirtiness-monsieur-stingy.ngrok-free.dev'
};

Every service class references environment.apiUrl as private base = environment.apiUrl, ensuring a single point of change when switching deployment targets.
